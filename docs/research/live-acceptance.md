# 线上验收

本报告汇总 2026-10-08 对本地候选版 0.5.0rc4+standalone.7 的授权验收。报告只描述实际执行的功能，不把接口目录数量当作验收数量。所有线上步骤都在隔离虚拟环境中运行，导入的包在运行前与候选 wheel 逐字节比对，不一致就拒绝执行。

## 已观察

- 在空的账号库中完成冷启动短信 App 登录，并用 App 签名账号读取核对身份。
- 读取账号资料和账号自己的草稿。
- 上传图片并从 CDN 读回，核对上传内容的字节一致。
- 创建并删除草稿。
- 执行一组仅针对测试账号自有内容的发布、收藏和评论操作，并验证清理结果。
- 本次冷启动的测试账号与主账号分别匹配各自身份，交叉身份读取未命中，两个账号都能读取各自草稿。
- 两种微信扫码流程都取得 Web SSO 会话字段，但 App 与 Web 请求均返回重新登录状态。
- 平台的图片上传分配接口现在要求 `file_infos` 条目带 `width` 和 `height`。缺少尺寸时返回 `status=failed`、`msg=文件信息缺失`；补上尺寸后同一请求在 `/upload/info` 与 `/upload/info/v2` 都返回 `status=ok`。
- 同一账号早前登录产生的旧别名 `personal` 会话返回 `status=relogin`，而同日新登录的两个会话仍通过身份核对。这是观察结果，不构成对原因或会话上限的结论。

本地 signer bundle 使用受支持 APK 与公开 loader 源码。离线签名自检和安装后运行验证通过。wheel 不含 APK、JAR、SO、账号库或浏览器配置。

## 发布门槛记录

run-24 使用 `.6` wheel 在门槛内构建签名器，并通过 13 项本地检查。生成的 loader SHA-256 为 `65e9a816ebb2ba7a167c3003f3a8218f34e3182c964592f795c3bce2c45ae197`。run-24 报告仍列出 3 条 `not run` 事项，且使用 schema 1 live record；它的 `release_ready` 字段与开放事项不一致。

run-26 使用同一 wheel、同一 loader 哈希、APK、schema 2 live record 和权属记录重新验收。12 项本地检查全部通过。发布前复核随后发现该记录绑定的是更早构建的 `.6` wheel，与当前源码构建出的 wheel 在包内 README 上有两段差异，记录不覆盖拟发布的字节。用 `.6` wheel 重跑线上验收时，上传步骤返回 `status=failed`，暴露出缺少图片尺寸字段的缺陷。

修复后包内 README 仍写着 `.6`，`account` 帮助索引也仍把登录描述成只用微信扫码，与已记录的登录结论矛盾，因此重建发布包并补了防回归测试。run-36 用最终 wheel（SHA-256 `2ca9af8ece4e105631e62c6c4043e1fa758c766e16031afd4e52028bc44293ff`）通过 12 项本地检查。run-37 加入绑定该 wheel 的 schema 2 live record 和 schema 2 权属记录，12 项本地检查全部通过，live 与权属记录有效，`open_items` 为空，`release_ready` 为 true。当前门槛明确检查两个不同账号的自身身份匹配、交叉身份拒绝、各自草稿读回、链接 JSON 的 SHA-256，以及权属记录列出的每个素材的摘要。最终发布摘要依据 run-37。原始门槛报告不随仓库分发。

## 分析推断

这些结果证明 CLI 对应版本能完成上列流程。它们支持以“接口参考加已验收 CLI 子集”的形式发布和交流。

## 未验证

- 448 条接口参考没有逐条进行线上调用。
- 两个账号的身份与草稿隔离已验证。现有线上记录没有设备标识断言，因此不证明两个账号需要或使用了不同物理设备。
- 群聊、房间、搜索、部分社交和其他历史路由没有完整线上验收。
- 结果不保证服务端未来继续兼容，也不构成对平台的授权。

原始证据包含本地账号别名和操作细节，保留在研究案件目录中，不随公开项目分发。公开报告不包含手机号、验证码、账号 ID、会话值或原始服务端响应。
